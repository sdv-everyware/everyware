# Decisions

One line per decision: when, what was asked, what was decided, why.

| Date | Question | Decision | Why |
|------|----------|----------|-----|
| 2026-11-02 | Demo theme for SDV Media on the RB3 | a smart home panel, not a car | the point is SDV Media for embedded devices |
| 2026-11-02 | One board or two devices? | two devices from the start: RB3 panel plus Cuttlefish vm0 | shows functions moving between devices |
| 2026-11-02 | MCP or AppFunctions first? | MCP | runs on SDV Media itself; AppFunctions need an Android phone |
| 2026-11-02 | Which AI agent? | a cloud agent on the laptop, MCP over the LAN | no internet needed on the panel |
| 2026-11-02 | What may an agent not do? | nothing is forbidden for the demo | demo; to be revisited for a product |
| 2026-11-03 | Where does the app live? | `packages/services/display_safety/utils/smarthome-app`, own git repo | harry's libraries are only visible under `display_safety` |
| 2026-11-03 | Keep harry's reducer pattern? | yes | it is harry's architecture; topic updates and RPC answers map onto actions |
| 2026-11-03 | Network in the app or in a bundle? | only bundles talk to the network | isolation, security, reuse ([4. Communication](../concepts/4-communication.md)) |
| 2026-11-11 | Agent instructions | open formats: `AGENTS.md` in everyware, ui-lib and every app, and skills in the Agent Skills format; the manifest links `everyware`'s `AGENTS.md` to the tree's top as `AGENTS.md` and `CLAUDE.md` | usable by any coding agent and by people; an agent opened on the tree finds the skills; `linkfile` is how AOSP puts files at the top |
| 2026-11-03 | Docs structure | concepts / solution / project, one idea per page | how Google and Apple developer docs are built |
| 2026-11-03 | Who brings up the network? | each device's product (RB3: oneshot service `net_bringup`, DHCP on eth0 and wlan0); this project only fixes the contract: DNS servers in `/data/vendor/net/resolv.conf` | devices differ in interfaces, drivers and firmware ([7. Extensions](../concepts/7-extensions.md#what-a-device-product-provides)) |
| 2026-11-05 | DHCP and the DNS contract | AOSP's `dhcpclient` (device/generic/trusty) instead of toybox `dhcp` with a hook script; the DNS servers are the properties `vendor.net.<if>.dns1..4` it publishes, not a file; the RB3 brings up wlan0 only | stock AOSP code and its SELinux policy; the hook, `ip` built for vendor (patch 0001) and the file in `/data/vendor` go away; one interface means one default route |
| 2026-11-03 | SELinux for the network pieces | own permissive domains (`net_bringup`, `sdv_dnsproxyd`) | bring-up; the logged denials become the policy |
| 2026-11-03 | DNS without netd | own daemon `dnsproxyd` on netd's socket, in its own repository; not the stock netd stack, not a resolver per bundle | `getaddrinfo()` works in every process; netd needs the framework and takes over routing ([7. Extensions](../concepts/7-extensions.md#why-not-the-stock-stack-why-not-a-resolver-per-bundle)) |
| 2026-11-03 | WeatherBundle | own APEX `com.everyware.weather`, Open-Meteo, Berlin, every 10 minutes, topic `weather` | free API without a key; one bundle per function |
| 2026-11-03 | Internet through an Android device, as SDV does in a car? | no: the house has no Android device, the panel goes to the internet itself | the product must work on its own |
| 2026-11-03 | Quality bar | production-ready, no workarounds | the project is meant to be used, not only shown |
| 2026-11-03 | HTTPS in a bundle | hyper + tokio-openssl + openssl (BoringSSL), SDV's own stack, in the bundle's process; not reqwest, not a separate fetch process | one TLS stack per process; reqwest's second stack cannot be linked next to SDV's ([7. Extensions](../concepts/7-extensions.md#https-from-a-bundle)) |
| 2026-11-03 | System time without the framework | chrony 4.9 (upstream, Android build in `vendor/sdv-everyware/third_party/chrony`), `time.android.com`; not toybox `sntp`, not our own client | the standard NTP implementation of Linux: step at boot, RTC sync, drift, NTS later ([7. Extensions](../concepts/7-extensions.md#system-time-chrony)) |
| 2026-11-03 | Where the repositories live | `vendor/sdv-everyware/everyware` and `vendor/sdv-everyware/dnsproxyd` | AOSP place for product code; `libopenssl` is already visible there |
| 2026-11-05 | Project name | SDV EveryWare: SDV Media as the OS of embedded devices; the smart home panel is the first device, not the project | all embedded devices are the target, not one |
| 2026-11-05 | Sizes of library components | fixed size per variant, fill on the variant, label box centred, marker = its own shape (as Google's own Figma files); no runtime resizing, no "fill container" | the two other ways needed harry patches; every patch moves away from mainline |
| 2026-11-05 | How the weather reaches the screen | WeatherServiceBundle → topic `weather` → DashboardServiceBundle → gRPC → harry process; the app never fetches | only bundles are SDV participants and talk to the network; the screen only draws |
| 2026-11-05 | A bridge bundle at all? | yes, `DashboardServiceBundle` between the topics and the harry process, as Google's HarSdvServiceBundle ↔ harry-app | the screen process is no SDV participant; the bridge keeps the last values and resends them after a UI restart; a new source is one subscription there ([bundles/dashboard/README.md](../../bundles/dashboard/README.md)) |
| 2026-11-06 | UI → bundle commands | the Wi-Fi bundle serves an SDV RPC `WifiService` (scan, connect, forget, disconnect; `catalog/wifi_service.proto`, vsidl `server`/`client { service: ... }`); the bridge calls it for every command of the gRPC stream and hands the answer back (`PublishWifiResult`) | a command has an outcome for its caller (a connect: joined or why not, a call that did not get through); only the bridge may call (authz `client`), the deadline is the client's (40 s) |
| 2026-11-05 | Where reusable UI behaviour lives | in ui-lib, at once (Overlay, Form, KeyboardDock, ListView, Scrollbar); an app presenter is one `view(&component)` per component; a use case (Wi-Fi) never enters the library | "we make a framework for the apps, not one use case" |
| 2026-11-05 | Keyboard | the screen's one keyboard dock (`#keyboard-dock`, open while a field has the focus), not a part of each sheet; as a system keyboard | a second form gets it for free; a sheet's set stays two variants |
| 2026-11-05 | Sheets over the screen | component sets the app draws (`#wifi-sheet`: state × step), the instance in an absolute wrapper frame, harry animates the variant switch; moving parts carry their own `AnimationOverride` | Figma's import drops "absolute" on an instance; harry does not inherit a parent's animation |
| 2026-11-05 | Lists | `ListView` with Android's scrolling physics (ported from the first app on the RB3) stepped per frame in the slot customizer, a `#scrollbar` with auto-hide; no 6-row limit | 20 networks, settings screens; the first app on the RB3 proved the physics on the board |
| 2026-11-05 | Icons inside list rows | glyph stacks (`#list-item/leading/<glyph>` at opacity 0, the code lights one), not a variant of an inner instance | harry does not swap a variant inside a list item (overrides.rs reads the global customizations only); opacity is per item and display-only |
| 2026-11-05 | Touch targets | `#icon-button` variants 72 × 72 around the visual circle; a slot grows to the variant around its centre | Material: 40 in 48, AAOS asks for 76; 48 px at the panel's top edge was too small |
| 2026-11-05 | Dropdown under the tiles | the status row is an absolute child of the root column, placed after the content in the tree; the root's top padding keeps its place | harry paints in child order, no z-index; fixed the same way in Figma by hand and in the generator |
| 2026-11-05 | Wi-Fi: who talks to the supplicant | a service bundle (`com.everyware.wifi`) over hostap's control protocol on an abstract unix socket (`-g@abstract:`); not the AIDL ISupplicant HAL (no scan), not a helper daemon | the bundle owns the device; no file, no DAC, SELinux alone decides ([bundles/wifi/README.md](../../bundles/wifi/README.md)) |
| 2026-11-05 | Wi-Fi: SELinux | its own domain `wifi_service_bundle` through `/product/etc/service_bundle_contexts` (the lifecycle manager's map), not a wider `untrusted_service_bundle`; both sides marked `socket_between_core_and_vendor_violators` on purpose | only this bundle may command the supplicant; the image has no framework and owns both sides |
| 2026-11-06 | Wi-Fi: the password | screen → gRPC loopback → bridge → SDV RPC (TLS between the bundles, the lifecycle's certificates) → bundle → supplicant; stored by the supplicant only | replaces the topic hop of 2026-11-05; the password is in no log and no topic |
| 2026-11-05 | Next protocols | Matter first (rs-matter in a bundle, virtual devices from connectedhomeip for demos), MQTT second, RTSP camera third; each protocol its own bundle, the screen protocol-agnostic | Matter is the standard of Google/Apple/Amazon; the same bundle shape as Wi-Fi |
| 2026-11-16 | The agenda on the dashboard | the right column shows the calendar bundle's agenda: a subheader per day and the events as list items with the start, a bar in the event's colour and the whole title; a tap on an event opens its details in a panel at the right; while no calendar is linked a card shows the setup page's QR code. The panel takes the news feed and drops it | the right column holds one thing; an agenda is what a household looks at on a wall panel; the news bundle stays for other screens |
| 2026-11-06 | News thumbnails | raw RGB 120 x 90, all of a feed in one message on a topic of their own, decoded and scaled in the bundle (`image` with `zune-jpeg`, memory-safe Rust); WebP not decoded, the row keeps its placeholder | the screen decodes nothing from the internet; the feed is not held back by its pictures; a late subscriber gets the last message of a topic, so one message brings every picture |
| 2026-11-06 | HTTPS for the bundles | one client, `libs/https` (hyper, tokio-openssl, BoringSSL, system CAs, redirects, size and time limits), used by the weather and the news | one TLS stack per process (`bssl_sys` once); one place for the limits |
| 2026-11-06 | The screen empty for 15 to 22 s after a boot (weather, news) | the bundles keep their last messages in SDV's bundle directory and publish them at their start; the bridge subscribes with `read_on_subscribe`; chronyd sets the clock from its last run (`-s`, started after the RTC); dhcpclient starts on the Wi-Fi connect | the data is on the screen with its first frame (8 s) and new at about 18 to 20 s, not 23 to 34 s; no new SELinux type, all SDV's or chrony's own mechanisms |
| 2026-11-16 | How the panel links a Google Calendar | like Home Assistant: Google's OAuth for a web application with PKCE (S256) and a one-time state; a QR code on the screen opens the panel's setup page on the local network, Google sends the phone to a static relay page on https, which sends it back to the panel; the setup page asks for the access first, read only (`calendar.events.readonly`, the default) or read and change (`calendar.events` as well), and what Google granted decides (the owner may untick the change on the consent screen); Google grants the events of all the account's calendars, the panel reads and changes the primary one; the tokens only on the panel; the OAuth client is the owner's, put on the panel by adb | Google's device flow does not allow the Calendar scopes; a server of our own would hold the tokens of every house; write access on a shared screen is the owner's choice, not the default ([bundles/calendar/README.md](../../bundles/calendar/README.md)) |
| 2026-11-17 | What the panel may do with an agenda event | in the event's panel: a QR code of its meeting link ("Join on phone") and of a Google Maps search for its place ("Directions"); with write access, Accept, Maybe and Decline on an invitation (the current answer marked) and Delete on the account's own event after a confirmation (a recurring event: this occurrence only). The screen asks the calendar bundle through the dashboard bundle (`CalendarService`, SDV RPC); the bundle takes a change only from the dashboard bundle and only for an event of its own last agenda that allows it, checks the rule again on Google's event and changes that version (`If-Match`), tells the others (`sendUpdates=all`), and publishes the new agenda before it answers; never on private or confidential events, nor on birthdays, Gmail's events or out of office | the phone, not the panel, opens links; a change is what a household does at a wall panel; the same path as Wi-Fi's commands; the screen cannot name any event or reach Google itself ([bundles/calendar/README.md](../../bundles/calendar/README.md)) |
| 2026-11-17 | The browser built only on request | `EVERYWARE_BROWSER` (product/everyware.mk, false by default): with it off, the image has no browser service, scripts or property, the panel no browser code (Soong's `everyware`/`browser`, the cfg `browser`) and the board no import of the browser's init file | nothing on the dashboard opens it; an experimental component with open security problems (#54) stays out of the image unless asked for |
